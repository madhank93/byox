## What this stage teaches

The payoff. An index is a **second b-tree** storing `(key, rowid)` pairs sorted
by key, so a lookup searches it for the value and gets back row ids, then
fetches only those rows from the table tree. A full scan is O(n); an index
lookup is O(log n) plus one read per match.

Deciding to use it is the smallest possible query planner: see a `WHERE` on an
indexed column, take the index path.

```
a WHERE lookup, two trees instead of one:

  full scan (stage 8)              index lookup (this stage)
  -------------------              -------------------------
  table b-tree                     index b-tree      table b-tree
      |                                 |                 |
   every leaf                     search for "Kenya"      |
   every row                            |                 |
   test the predicate             -> rowids 47, 91 -------+
      |                                                   |
   O(n)                                              fetch 2 rows
                                                     O(log n) + 2

an index record is (key, rowid) -- the row id is its LAST value, which is
the handle back into the table tree.
```

## Go you'll reach for

- The same page reader, pointed at index pages (`0x0a` leaf, `0x02` interior).
- A schema lookup for an index whose `tbl_name` matches and whose SQL names the
  filtered column.

## Hints

<details><summary>Nudge</summary>

An index record's last value is the row id.
</details>

<details><summary>Approach</summary>

Same decoder, different tree — which is the payoff for keeping the record
reader generic back at stage 3.
</details>

<details><summary>The API</summary>

Index pages are `0x0a` (leaf) and `0x02` (interior) — the same traversal
with different type bytes. An index record's values are the key followed by
the row id, so the row id is the last one.
</details>
