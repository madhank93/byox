## What this stage teaches

Your server becomes a client: it takes the questions it was asked, sends them
upstream, and merges the answers. This is what a resolver does, and it is the
first time your **encoder and decoder meet each other** rather than the tester —
so any asymmetry between them, invisible until now, surfaces immediately.

The wrinkle: upstream resolvers commonly reject multi-question packets, so an
N-question query is split into N single-question queries and the answers
reassembled under the original ID.

```
one multi-question query, N upstream queries:

  client                  your server                 upstream
    |  Q: a.com, b.com        |                          |
    |------------------------>|                          |
    |                         |  Q: a.com  (id 1234)     |
    |                         |------------------------->|
    |                         |            A: a.com=1.2.3.4
    |                         |<-------------------------|
    |                         |  Q: b.com  (id 1234)     |
    |                         |------------------------->|
    |                         |            A: b.com=5.6.7.8
    |                         |<-------------------------|
    |  A: both answers,       |                          |
    |     original ID         |                          |
    |<------------------------|                          |

upstream resolvers commonly refuse multi-question packets, so you split and
reassemble -- which is the first time your encoder and your parser are used
against each other rather than against the tester.
```

## Go you'll reach for

- `net.Dial("udp", upstream)` per query.
- The encoder from stages 2-4 and the parser from 5-7, now both directions.

## Hints

<details><summary>Nudge</summary>

The upstream address arrives as `--resolver <ip>:<port>`.
</details>

<details><summary>Approach</summary>

Test your own encoder against your own parser directly. If a round trip does
not survive, forwarding cannot work.
</details>
