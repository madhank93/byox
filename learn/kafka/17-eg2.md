## Core concept

The moment Kafka's design shows itself: the bytes on disk are **the same bytes
that go on the wire**. A partition's log segment already holds record batches in
protocol format, so serving a fetch is reading a file range and sending it —
no decoding, no re-encoding.

That identity is why Kafka is fast. Real brokers push it further with
`sendfile`, handing the file straight to the socket without the data ever
entering user space.

```
the same bytes, three places:

   producer                broker disk                consumer
      |                        |                          |
      |  Produce: batch bytes  |                          |
      |----------------------->| append verbatim          |
      |                        | 00000...0.log            |
      |                        |                          |
      |                        | read the range           |
      |                        |------------------------->|
      |                        |     Fetch: same bytes    |

no decode, no re-encode, no translation layer. that identity is why a
broker can serve fetches with sendfile() and never copy the data into
user space at all.
```

## Go APIs

- `os.ReadFile` on `/tmp/kraft-combined-logs/<topic>-<partition>/…​.log`.
- The bytes copied into the response's records field verbatim.

## Hints

<details><summary>Nudge</summary>

The records field is a compact bytes field: a varint length, then the bytes.
</details>

<details><summary>Approach</summary>

You do not need to understand the batch's contents to serve it — only its
length.
</details>

<details><summary>Implementation</summary>

The records field is compact bytes: an unsigned varint of `len+1`, then the
file's bytes unchanged. No decoding is needed to serve them.
</details>
