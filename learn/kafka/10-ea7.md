## What this stage teaches

The big one. To answer about a real topic the broker reads
`__cluster_metadata-0/…​.log` — Kafka stores its own cluster state **as a Kafka
topic**, in the same record-batch format as any other. Metadata is not a
separate database; it is a log.

So you parse: a record batch header (base offset, batch length, CRC, magic,
record count), then records, each varint-length-prefixed, then the typed
metadata payloads inside them — topic records and partition records identified
by a type byte.

```
a record batch, as stored on disk and sent on the wire:

 +-------------+--------------+-----+-------+-------------------+---------+
 | base offset | batch length | CRC | magic | attributes .. seq | records |
 |    8 B      |     4 B      | 4 B |  1 B  |                   |  count  |
 +-------------+--------------+-----+-------+-------------------+---------+
                                                                     |
    +----------------------------------------------------------------+
    v
 +--------+------+-----------+--------+-----+-------+
 | length | attr | ts delta  | offset | key | value |    each length a varint,
 | varint | 1 B  | varint    | delta  |     |       |    signed ones zigzagged
 +--------+------+-----------+--------+-----+-------+

__cluster_metadata uses this same format -- its records just carry a type byte
saying "topic" or "partition" instead of user data.
```

## Go you'll reach for

- A byte reader with `skip`, `int32`, `varint` helpers.
- Signed varints use **zigzag** encoding; protocol lengths do not.

## Hints

<details><summary>Nudge</summary>

Topic records carry name and UUID; partition records carry the partition id and
the topic UUID they belong to.
</details>

<details><summary>Approach</summary>

Build the batch parser carefully — `Fetch` reads ordinary partition logs with
exactly the same code.
</details>

<details><summary>The API</summary>

Signed values inside records use zigzag varints — `(n >> 1) ^ -(n & 1)` to
decode — while protocol lengths use plain unsigned ones. Mixing them shifts
every later field.
</details>
