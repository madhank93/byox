## Core concept

A function's call environment hangs off the environment where the function was
**defined**, not where it was called. That one choice is the whole of closures:
a returned inner function keeps working because the chain it captured is still
reachable through it, even though the outer call has returned.

Hanging it off the *caller's* environment instead would give you dynamic
scoping — a different language, and one where a function's meaning depends on
who calls it.

```
fun makeCounter() {          the closure keeps the chain alive:
  var i = 0;
  fun count() {                count's Closure --> [ i: 0 ] --> globals
    i = i + 1;                                        ^
    print i;                                          |
  }                            after makeCounter returns, this environment
  return count;                is unreachable from the call stack but still
}                              referenced by count -- so it survives

var c = makeCounter();
c();  // 1     each call makes a CHILD of that captured environment,
c();  // 2     so i keeps incrementing rather than resetting

hanging the call off the CALLER's environment instead would be dynamic
scoping: the same function would mean different things per call site.
```

## Go APIs

- A `Closure *Environment` field on `LoxFunction`, set at declaration time.

## Hints

<details><summary>Nudge</summary>

`makeCounter()` returning an inner function that increments a captured variable
is the canonical test.
</details>

<details><summary>Approach</summary>

Go's garbage collector keeps the captured environment alive for you — in a
language with manual memory management this is where closures get hard.
</details>

<details><summary>Implementation</summary>

Set `Closure` when the `FunctionStmt` is executed, not when the function is
called — that is the difference between lexical and dynamic scoping.
</details>
