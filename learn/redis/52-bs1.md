## What this stage teaches

`XREAD BLOCK <ms>` waits for new entries instead of returning empty. This is the
first command whose handler does not return promptly, and it introduces the rule
that governs every blocking command in the rest of the course: **never hold the
keyspace lock while waiting.** A blocked reader holding the lock deadlocks the
writer that would unblock it.

Timing out returns a null array (`*-1\r\n`), which is distinct from an empty
array.

```
a blocked reader must NOT hold the keyspace lock:

  wrong                              right
  -----                              -----
  lock()                             loop:
  while no data:                       lock()
      sleep()      <-- writer can       check for data
  read()               never get in     unlock()          <-- released
  unlock()                              if found: reply, done
                                        sleep(20ms)       <-- outside the lock

the writer that would unblock you needs the same lock. holding it across the
sleep is a deadlock that looks exactly like a hang.
```

## Go you'll reach for

- A loop: take the lock, check, release, sleep briefly, repeat.
- Or a condition variable / per-key channel, if you prefer signalling to polling.
- `time.Now()` against a deadline for the timeout.

## Hints

<details><summary>Nudge</summary>

`BLOCK 0` means block forever — the next stage.
</details>

<details><summary>Approach</summary>

Polling every few milliseconds is legitimate here and much easier to get right
than a notification scheme. Just keep the sleep outside the lock.
</details>

<details><summary>The API</summary>

Because each connection is its own goroutine, blocking one blocks only that
client. That is exactly why the goroutine-per-connection design pays off here.
</details>
