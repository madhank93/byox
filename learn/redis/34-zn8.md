## What this stage teaches

The master now writes to a connection *nobody asked it to*: after applying a
write command from client A, it forwards those bytes to replica B. This is the
first cross-connection side effect in the program, and it breaks the
one-goroutine-owns-one-connection assumption you have relied on since stage 4.

A replica connection therefore needs its own write mutex. Two client goroutines
propagating at once will otherwise interleave halves of two commands into one
stream, producing bytes that parse as neither.

## Go you'll reach for

- A slice of replica connections on the server, guarded by a mutex.
- A per-replica `sync.Mutex` around each write.
- The RESP encoder from the AOF stages — propagation sends the command verbatim.

## Hints

<details><summary>Nudge</summary>

Propagate writes only, using the same read/write classification the AOF filter
uses.
</details>

<details><summary>Approach</summary>

Replicas send no reply to a propagated command, so don't wait for one. The
stream is one-directional until `REPLCONF GETACK` at stage 37.
</details>

<details><summary>The API</summary>

Guard the replica *list* and each replica's *writes* separately. One lock for
both serialises every client behind the slowest replica.
</details>
