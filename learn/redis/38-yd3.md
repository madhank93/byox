## What this stage teaches

The same ACK after real traffic, which is where an offset that was accidentally
right becomes visibly wrong. Every byte the master sent counts: the propagated
`SET`s, and each earlier `GETACK` — including the ones the replica replied to.
The replica's reply bytes do **not** count; the offset measures the master's
stream, not the conversation.

## Go you'll reach for

- Nothing new. This stage tests the accounting from stages 36 and 37.

## Hints

<details><summary>Nudge</summary>

If the number is short by exactly the length of one `GETACK`, you are not
counting the GETACK itself after replying.
</details>

<details><summary>Approach</summary>

Print the offset alongside each command while debugging and add the expected
lengths by hand — `*3\r\n$8\r\nREPLCONF\r\n$6\r\nGETACK\r\n$1\r\n*\r\n` is 37
bytes. Arithmetic beats guessing here.
</details>
