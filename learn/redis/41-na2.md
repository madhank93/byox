## Core concept

The real `WAIT`: writes have gone out, and the master must ask every replica for
its offset (`REPLCONF GETACK *`), then block until either `numreplicas` have
acknowledged at least the current offset, or the timeout expires — returning
however many made it. It is a quorum with a deadline, and it is the hardest
concurrency in the course so far.

Two things make it tricky. The ACKs arrive asynchronously on replica
connections, so the counting happens in a different goroutine from the waiting.
And sending `GETACK` advances the master's own offset, so the target must be
captured *before* you send.

```
WAIT 2 500

  t=0    capture target = master offset          (BEFORE sending GETACK,
         broadcast REPLCONF GETACK * to all       because sending advances it)
         acked = 0 / need 2
  t=12   replica1 ACK >= target   -> acked = 1
  t=31   replica2 ACK >= target   -> acked = 2   -> return :2  (early!)
  ...    (t=500 deadline never reached)

  if only one replica ever answers:

  t=0    ... broadcast ...
  t=12   replica1 ACK          -> acked = 1
  t=500  deadline              -> return :1     -- however many made it

returning as soon as the count is met is required, not an optimisation:
the tester measures elapsed time.
```

## Go APIs

- `time.After(timeout)` in a `select`, against a channel fed by arriving ACKs.
- A per-replica `ackOffset` field updated when `REPLCONF ACK` arrives.
- `sync.Mutex` or channels — but pick one and stay with it.

## Hints

<details><summary>Nudge</summary>

Capture the target offset, broadcast `GETACK`, then wait for acknowledgements
of at least that value.
</details>

<details><summary>Approach</summary>

Returning early once enough replicas answer is required, not an optimisation —
the tester measures elapsed time.
</details>

<details><summary>Implementation</summary>

Replicas that were already at the target before you sent `GETACK` still count.
Check current state first, then wait only for the shortfall.
</details>
