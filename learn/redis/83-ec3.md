## What this stage teaches

`BLPOP key 0` waits until an element exists, then pops it. This is the primitive
that makes Redis a work queue — and it adds a requirement `XREAD BLOCK` did not
have: when several clients are blocked on the same key and one element arrives,
**exactly one** client may get it. A blocking read can serve everybody; a
blocking pop must not.

## Go you'll reach for

- The stage-52 wait loop, but re-checking *and popping* under the same lock.

## Hints

<details><summary>Nudge</summary>

The reply is a two-element array: the key, then the value.
</details>

<details><summary>Approach</summary>

Check-and-pop must be one critical section. Checking under the lock, releasing,
then popping is how two clients both receive the same element.
</details>

<details><summary>The API</summary>

Redis serves blocked clients in arrival order. Polling clients won't reproduce
that exactly, and the tester does not require it — but know that you're
approximating.
</details>
