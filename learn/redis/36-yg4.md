## What this stage teaches

The replica side of propagation: read commands off the master connection and
apply them, silently — no replies. And this is where the offset finally has to
be counted, because the replica must track **how many bytes of the replication
stream it has processed**.

Count the bytes of each command *as encoded on the wire*, after processing it.
Counting characters, or commands, or bytes-before-processing, all produce an
offset that is close enough to look right and wrong enough to fail stage 38.

## Go you'll reach for

- The same parse loop, reading from the master connection.
- An `offset += len(encodedCommand)` after each command.

## Hints

<details><summary>Nudge</summary>

Applied commands must be visible to normal clients — `GET` on the replica sees
what the master `SET`.
</details>

<details><summary>Approach</summary>

Have the parser report how many bytes it consumed per command, rather than
re-encoding the parsed command to measure it. Re-encoding is where subtle
mismatches creep in.
</details>

<details><summary>The API</summary>

A propagated command must not be answered on the master connection. Only
`REPLCONF GETACK` gets a reply — that's the next stage.
</details>
