## Core concept

Now you have to actually parse. Clients send every command as a **RESP array of
bulk strings**: `*2\r\n$4\r\nECHO\r\n$3\r\nhey\r\n`. The parser you write here
serves the next hundred stages, so it is worth building properly: read the array
length, then that many bulk strings, each a `$<len>` line followed by exactly
that many bytes and a CRLF.

Bulk strings are binary-safe. Use the declared length — never split on
whitespace, and never assume the payload is printable.

```
every command a client sends is an array of bulk strings:

   ECHO hey
 +----+------+-------+------+------+
 | *2 | $4   | ECHO  | $3   | hey  |     each line ends \r\n
 +----+------+-------+------+------+
   ^    ^                 ^
   2    length of the     the bytes -- binary-safe, so use the
   args next bulk string  length and never split on whitespace

 replies use the same five type bytes:
   +OK        simple string      :42        integer
   -ERR ...   error              $5\r\nhello bulk string  ($-1 = null)
   *2 ...     array
```

## Go APIs

- `strconv.Atoi` on the digits after `*` and `$`.
- `io.ReadFull(reader, make([]byte, n))` for the payload.
- A `[]string` return, then a `switch strings.ToUpper(args[0])`.

## Hints

<details><summary>Nudge</summary>

The reply is a bulk string: `$3\r\nhey\r\n` — length in bytes, then the bytes.
</details>

<details><summary>Approach</summary>

Write one function that reads a whole command and returns `[]string`. Every
later stage calls it, and the dispatch `switch` grows around it.
</details>

<details><summary>Implementation</summary>

Command names are case-insensitive (`ECHO`, `echo`, `Echo`); keys and values are
not. Normalise only the command name.
</details>
