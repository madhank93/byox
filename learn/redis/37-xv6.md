## Core concept

`REPLCONF GETACK *` asks a replica for its offset, and the replica answers
`REPLCONF ACK <offset>`. The trap is precise and famous: the reported offset
**excludes the GETACK command itself** — you reply with the offset as it stood
before that command, then add its bytes.

With no prior commands the correct answer is 0, which is exactly the value a
buggy implementation also produces, so this stage passes easily and the bug
surfaces at the next one.

```
the replica's offset, byte by byte:

  received                            offset   replies
  ------------------------------------------------------------
  (nothing yet)                            0
  SET foo bar        (31 bytes)      0 -> 31
  REPLCONF GETACK *  (37 bytes)           31   "ACK 31"   <-- reply FIRST
                                     31 -> 68              then add 37
  SET baz qux        (31 bytes)      68 -> 99
  REPLCONF GETACK *  (37 bytes)           99   "ACK 99"
                                     99 -> 136
  ------------------------------------------------------------

the reply reports the offset BEFORE this GETACK is counted.
add the bytes after answering, never before -- and note the replica's own
reply bytes are never counted at all: the offset measures the master's stream.
```

## Go APIs

- A `REPLCONF GETACK` case on the replica's master-connection loop.
- An array reply: `REPLCONF`, `ACK`, the offset as a string.

## Hints

<details><summary>Nudge</summary>

Reply first, then add this command's byte count to the offset.
</details>

<details><summary>Approach</summary>

Write the offset update as a single line at the end of the loop, and make the
GETACK case read the value *before* it runs. One ordering rule, in one place.
</details>
