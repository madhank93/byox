## Core concept

The mechanism behind `WATCH`. Every key needs a version that increments on
modification; `WATCH` records the current version, and `EXEC` compares. If any
watched key moved, the transaction is abandoned and `EXEC` returns a **null
array** (`*-1\r\n`) — distinct from the empty array of stage 60, and clients
distinguish them.

Versions beat storing a copy of the value: they are cheap, and they catch a
write that set the key back to its original value, which a value comparison
would miss.

## Go APIs

- `map[string]uint64` of versions, incremented under the keyspace lock.
- A comparison loop at the top of `EXEC`.

## Hints

<details><summary>Nudge</summary>

Bump the version in every mutating path — `SET`, `INCR`, expiry-driven deletion.
</details>

<details><summary>Approach</summary>

Bump inside the same critical section as the mutation. A version updated outside
the lock can be observed out of order with the value it describes.
</details>

<details><summary>Implementation</summary>

A transaction abandoned this way still resets the connection: clear `inMulti`,
the queue and the watch set.
</details>
