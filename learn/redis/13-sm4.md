## Core concept

Expiry timestamps in RDB come as an opcode *before* the value type byte:
`0xFD` is a 4-byte expiry in **seconds**, `0xFC` an 8-byte expiry in
**milliseconds**. Both are **little-endian**, which is worth flagging because
almost every other network format you meet in these courses is big-endian —
RDB is a disk format, so it follows the machine, not the wire.

Keys already expired at load time must not appear in `KEYS` or `GET`. The
lazy-expiry check from stage 7 handles that for free if the deadline is stored
in the same field.

## Go APIs

- `binary.LittleEndian.Uint32` and `binary.LittleEndian.Uint64`.
- `time.UnixMilli(ms)` / `time.Unix(sec, 0)`.

## Hints

<details><summary>Nudge</summary>

The expiry opcode comes first, then the value type byte, then key and value —
so read it as a prefix and carry it into the pair you're about to read.
</details>

<details><summary>Approach</summary>

Reuse the `expireAt` field from stage 7 rather than adding a second expiry
mechanism. One deadline field, one check, both paths.
</details>

<details><summary>Implementation</summary>

`time.UnixMilli` takes milliseconds since the epoch directly. Convert once, at
parse time — storing raw integers and converting at every read invites a
seconds/milliseconds mix-up.
</details>
